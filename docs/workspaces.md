# 工作目录与仓库关系

推荐用私有仓库保存个人资料，通过 `engine/` submodule 固定公开代码版本。也可以使用任意已有的独立数据目录，或在代码仓库内使用默认布局；具体上手步骤和统一 `config.json` 配置见[工作区配置](../config/README.md#工作区配置)。

## 两边维护什么

| 公开代码仓库 / 私有侧的 `engine/` | 私有数据工作区 |
|---|---|
| 通用代码、skill、文档、配置模板、功能测试 | 标准化来源、登记、实际配置、专用评测、个人操作记录 |
| 提交通用能力与行为变化 | 提交资料变化、私有说明和固定的代码引用 |
| 通用功能测试使用虚构数据 | 专用评测按私有工作区约定执行 |

通用文件只在公开仓库维护；私有根目录无需复制源码、通用文档或模板，也无需设置旧启动代理或 skill 链接。真实索引与执行账本属于本地运行状态；是否将标准化来源和登记纳入 Git，由数据工作区决定。

原始输入由调用者指定，保持只读，可以位于代码和数据目录之外。workspace 选择导入结果与维护状态的保存位置，不代替导入参数。来源、登记、索引和账本由对应程序维护，见[产物维护边界](usage.md#产物维护边界)。

## 日常操作与代码升级

完成配置后，从 `engine/` 执行导入、维护及索引构建命令；数据 Git 检查与提交在私有根目录执行。两个 skill 位于 `engine/.agents/skills/`，私有开发约定应明确加载位置和个人操作记录的保存位置。

通用代码在公开仓库修改、测试和提交。可以在独立公开 checkout 开发，也可以在 submodule 的开发分支工作；随后将公开提交推送，在私有 `engine/` 获取并检出已验证的 commit，再提交私有 gitlink 更新。使用 reusable workflow 时，将私有调用 workflow 的引用固定到同一 commit。submodule 不自动跟随公开主线。

从代码目录运行通用测试：

```bash
env -u LEARN_CORPUS_DATA_ROOT -u LEARN_CORPUS_CONFIG venv/bin/python -m pytest
```

通用测试自动选用空的虚构配置，不读取开发机的个人配置；目录隔离测试自行准备虚构数据与配置。专用评测及个人验证记录按私有工作区约定维护。

## 数据版本、代码版本与运行版本

首次导入可以使用非 Git 数据目录。`check_corpus` 在数据根目录不是 Git 顶层或尚无 HEAD 时跳过 Git 变更对照，仍检查来源与登记。构建 Actions 发布包需要数据 Git 历史。

私有数据 commit 通过 gitlink 固定代码 commit。发布包的 `commit` 表示构建 workflow 的数据仓库 HEAD，可从该 HEAD 追溯代码版本；`release.json` 为 version 2。构建程序校验代码 checkout 与 gitlink 一致且代码工作区干净。

Actions 构建通过 `--repository owner/name` 指定预期数据仓库，部署配置通过 `repository` 指定同一仓库标识。真实索引 artifact 保存在构建它的私有仓库中。数据提交、代码升级、索引构建、部署和服务重启分别执行；更新代码引用或 workspace 配置不会自动切换运行中的索引。
